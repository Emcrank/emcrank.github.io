My Engineering Rules of Thumb

[01]
Config Over Hardcoding

Logic shouldn't care about environmental details. Secrets, URLs, and API keys belong strictly in options patterns and configuration models—never baked into the execution code. Swap the environment, not the codebase.

[02]
Design for the Swap

Always write code assuming the third-party provider will change. Keep your core mechanics generic (the "how") and isolate provider-specific implementations inside configurations or wrappers (the "who"). Swapping an API should be a config tweak, not a logic rewrite.

[03]
Interface-First & DI-Ready

Loose coupling isn't optional. I build components interface-first, with explicit dependency declarations inside constructor signatures. This keeps the codebase highly testable, mockable, and painless to maintain.

[04]
Strict Boundary Maintenance

Don't bleed layers. Data models (DTOs) should stay isolated from business services, and UI components shouldn't touch direct data-fetching mechanics. Clean boundaries prevent cascading bugs when structures change.

[05]
Keep it Simple

If a task needs to be done more than twice, it deserves a script. Manual processes invite human error.
